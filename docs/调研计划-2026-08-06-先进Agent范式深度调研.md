# 调研计划：最先进 Agent 范式深度调研（2026-08-06）

> 状态：计划待执行
> 目标：系统性找到并消化当前最先进的 agent 范式，产出一份"方方面面"全覆盖的范式图谱，
> 并基于本项目 `backend/agent/` 现状（见 `docs/任务记录-2026-08-06-Agent模块深度解析.md`）
> 输出可落地的演进路线图。
> 方法论红线：继承项目传统——**真跑一遍才算数**，任何范式结论必须有 PoC 或基准数据支撑，不接受纯叙事采纳。

---

## 1. 调研目标与成功标准

### 1.1 目标拆解

| # | 目标 | 验收标准 |
|---|---|---|
| G1 | 建立**先进 agent 范式全景图谱**（12 大维度，见 §3） | 每个维度有：代表范式 ≥2、代表论文/工程出处、适用边界、与本项目的差距分析 |
| G2 | 确定**本项目的目标范式**（不是照搬最炫的，而是最适配投资决策分析场景的） | 产出决策记录（ADR 形式）：选型结论 + 理由 + 被否方案 |
| G3 | 用**真实基准**验证候选范式收益 | 在 golden trajectory 评测集上，候选范式 vs 现有 ReAct+模板，量化对比（任务完成率/轨迹效率/token 成本/置信度准确性） |
| G4 | 输出**演进路线图**（P0/P1/P2 分级，与现有待办合并） | 每一项有工作量估算、风险、验证方式 |

### 1.2 明确不做

- 不做框架迁移评估（如整体换 LangGraph/AutoGen）——本项目自研骨架已被证明适配自身场景，调研聚焦**范式与机制**，不是换框架。
- 不追求学术 SOTA 复现——只取工程可落地的部分。

## 2. 调研方法论（四阶段漏斗）

```
阶段 A 广度扫描（信息收集）
   ↓  产出：信息源清单 + 范式候选长名单（~30 项）
阶段 B 深度精读（每维度 2-3 个代表深挖）
   ↓  产出：12 维范式图谱 + 差距分析矩阵
阶段 C 原型验证（挑 top 3-5 范式做 PoC）
   ↓  产出：PoC 分支 + 基准对比数据
阶段 D 综合决策（选型 + 路线图）
      产出：调研总册 + ADR + 演进路线图
```

**纪律**：
- 每个范式必须回答四个问题：解决什么问题？代价是什么？失败模式是什么？我们有没有这个问题？
- 一切"先进"结论必须对照本项目已踩过的坑（字段漂移、ReAct 死路径、完美后见高估）做失败模式审查。

## 3. 范式调研矩阵（12 维度全覆盖）

### 维度 1：执行范式与控制流（核心）

| 调研项 | 关键出处 | 对照本项目 |
|---|---|---|
| ReAct（现有基线） | Yao et al. 2022 | ✅ 已实现（run_stream） |
| Plan-and-Execute / ReWOO | ReWOO (2023)、LangGraph plan-and-execute | 🟡 有 planning 但默认关闭、未与执行闭环 |
| Reflexion / Self-Refine | Shinn et al. 2023 | 🟡 有 [REFLECT] 正则解析，无"失败后重跑"闭环 |
| LLMCompiler（DAG 并行规划） | Kim et al. 2023 | 🟡 模板有 parallel_groups，但 ReAct 路径无 DAG 并行 |
| Orchestrator-Workers（lead agent + 子代理） | Anthropic《Building Effective Agents》、Anthropic multi-agent research system 博客 | ❌ 未实现 |
| CodeAct（代码即行动） | Wang et al. 2024 | ❌ 未实现；data_query 工具是雏形 |
| Workflow graphs / 状态机编排 | LangGraph、Temporal 持久化执行 | 🟡 模板是静态的，无图状态/断点续跑 |
| Agent teams / swarm / handoff | OpenAI Agents SDK handoffs、AutoGen | ❌ 未实现，需评估是否过度设计 |

**决策焦点**：本项目 31 个工具 + 投资决策漏斗，重点评估 **Plan-and-Execute + LLMCompiler DAG 并行** 与 **orchestrator-workers** 两条路线。

### 维度 2：上下文工程（当前最大短板之一）

| 调研项 | 关键出处 |
|---|---|
| 上下文压缩（compaction / summarization） | Claude Code / Manus《Context Engineering for AI Agents》 |
| KV-cache 友好的提示结构（稳定前缀、追加式上下文） | Anthropic prompt caching 文档 |
| Just-in-time 检索替代预加载（让 agent 按需读文件/查表，而非塞满 system prompt） | Anthropic code execution with MCP 博客 |
| 结构化笔记 / scratchpad（agent 自维护工作记忆文件） | Manus 经验、SWE-agent |
| 子代理上下文隔离（lead 只看结论不看过程） | Anthropic multi-agent 博客 |
| token 预算显式管理 | 本项目 `_trim_history` 是字符预算，需升级为 token 预算 |

**对照**：本项目 `DATABASE_SCHEMA_CONTEXT` 全量注入 + 历史滑窗 8000 字符——调研重点：schema 按需检索化、工具结果落盘引用化（返回 artifact id 而非全文回灌）。

### 维度 3：记忆系统

| 调研项 | 关键出处 |
|---|---|
| 情景/语义/程序记忆三分法 | 记忆类综述、MemGPT/Letta 分层记忆 |
| 技能库（skill library）：成功经验沉淀为可复用流程 | Voyager (2023) |
| 跨会话持久记忆 vs 会话内记忆 | Letta、ChatGPT memory 产品形态 |
| 记忆写入/检索/遗忘策略（什么值得记、何时失效） | 与本项目 data_version 失效机制对照 |

**对照**：本项目 `SessionMemory` 是进程内、TTL 30 分钟、仅摘要提示。调研重点：跨会话"分析结论记忆"（如"SA1 2025 已被分析过，NPV 为正"）是否值得做、如何防陈旧结论污染。

### 维度 4：工具系统

| 调研项 | 关键出处 |
|---|---|
| MCP（Model Context Protocol）：工具互操作标准 | modelcontextprotocol.io |
| 工具检索/动态装载（31+ 工具时 schema 膨胀问题） | ToolLLM、Gorilla、Anthropic programmatic tool calling |
| 工具输出契约与 schema 治理 | 本项目 tool_contracts.py 是雏形，调研业界做法（Pydantic 契约测试） |
| 并行工具调用与依赖推断 | LLMCompiler、OpenAI parallel function calling |
| 工具沙箱与最小权限 | 与本项目 SQL 白名单对照 |

### 维度 5：规划与任务分解

| 调研项 | 关键出处 |
|---|---|
| 层级规划（高层目标 → 子目标 → 动作） | HuggingGPT、ADaPT |
| 树搜索 / 多路径择优（ToT/GoT） | Tree of Thoughts (2023) |
| 规划的 structured output 化（JSON mode 替代自由文本解析） | 本项目 P2 待办 3 |
| 动态重规划（观察后修订计划） | LangGraph replan 模式 |

### 维度 6：反思与自我修正

| 调研项 | 关键出处 |
|---|---|
| Reflexion 闭环（失败 → 语言反思 → 注入下轮重试） | Shinn et al. 2023 |
| Critic/Verifier 独立评审代理 | LLM-as-judge 家族、self-consistency |
| 数值自校验（投资场景特有：NPV/IRR 量纲与合理性检查） | 领域定制，需自研设计 |

**对照**：本项目置信度推断已是"不信任 LLM 自述"的正确方向；调研补齐的是**轨迹级**反思（工具选错/参数错时的自纠）。

### 维度 7：多智能体协作

| 调研项 | 关键出处 |
|---|---|
| Supervisor 模式（lead 分派 + 综合） | Anthropic multi-agent research system（token 代价 ~15x，需成本评估） |
| 领域专家代理分工（市场分析师/财务分析师/风险分析师） | 与本项目 Truth→Forecast→Decision 三层框架天然对齐 |
| 辩论/交叉验证模式 | multi-agent debate |
| **反面证据**：何时多代理不如单代理（成本、误差传播、协调开销） | Anthropic 博客自身的 lessons learned |

**决策焦点**：投资决策场景是否值得为"深度研究类查询"引入 2-3 个专家子代理，而日常查询保持单代理——分层策略。

### 维度 8：评估体系（本项目最大短板，2/10）

| 调研项 | 关键出处 |
|---|---|
| 三层评估：工具调用正确性 / 轨迹质量 / 最终输出 | 2026 年 agent eval 主流分层 |
| Golden trajectory 黄金集 + 回归 CI | 本项目 test_agent_golden_trajectories.py 雏形 |
| LLM-as-Judge（配对比较、rubric 评分、judge 偏差控制） | DeepEval/Confident AI 实践、Agent-as-a-Judge (arXiv 2508.02994) |
| 轨迹评估指标：冗余步数、工具选错率、参数错误率 | τ-bench、AgentBench 类基准 |
| 在线评估：用户采纳率、报告引用率 | 产品级指标 |

**硬性产出**：调研结束时必须有 **20 条黄金轨迹 + CI 门禁**，这是所有后续范式迭代的"测量仪"——没有它任何"更先进"都无从证明。

### 5.1 PoC 候选（预判，阶段 B 后确认）

1. **Plan-and-Execute + DAG 并行**（LLMCompiler 思路）：预期提升完整可行性分析的波次并行度，替代静态 parallel_groups。
2. **上下文工程改造**：schema 按需检索 + 工具结果 artifact 化回灌，目标把单轮 ~36k tokens 降 40%+。
3. **orchestrator-workers 深度研究模式**：仅对"完整可行性"类查询启用 2-3 个专家子代理，量化 15x 成本换质量是否成立。

（备选 4：记忆系统升级——跨会话结论记忆 + Redis 持久化，风险是陈旧结论污染，PoC 需先设计失效策略。）

### 5.2 黄金轨迹集设计（D6-D7 细节）

- 20 条覆盖：NEM 单区域深分析 ×4、WEM ×3、跨区域对比 ×3、数据探索 SQL ×3、降级路径（LLM 挂）×3、对抗性（注入式 query、越权 SQL）×2、多轮追问 ×2。
- 每条记录：期望工具序列（允许超集）、必含关键指标、token 上限、时延上限、置信度期望。
- 挂 CI：`pytest tests/test_agent_golden_trajectories.py` 离线模式（mock LLM 轨迹回放）+ 每周一次真实 LLM 回归（记录成本）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| "先进范式"与场景错配（投资决策要可审计，不要黑箱自主性） | 所有 PoC 以"可审计性不退化"为硬约束：轨迹可回放、数值可溯源到工具 |
| 多代理成本失控 | PoC 强制记录 token/美元，设定"单位质量成本"否决线 |
| 调研变成框架崇拜 | §1.2 明确不换框架；源码只读架构不引依赖 |
| 没有测量仪就迭代 | 黄金轨迹集是阶段 C 的**前置**任务，不可跳过 |
| 时间超支 | 阶段 B 每维度限时半天，图谱允许"该维度本项目无需求"的空结论 |
