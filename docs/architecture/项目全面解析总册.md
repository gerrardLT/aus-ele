## 1. 项目定位与目标

### 1.1 这是什么项目

`aus-ele` 是一个能源市场分析工作区，当前包含两条主线：

- 澳洲电力市场分析主线：围绕 AEMO 体系下的 NEM / WEM 数据，提供 `Current Market -> Forward Opportunity Outlook -> Market Entry Conclusion` 的市场进入与收益判断链
- Fingrid 数据主线：围绕芬兰 Fingrid 数据集，提供独立的数据同步、聚合、展示和导出能力

它不是自动交易系统，也不是投资自动决策系统。它更接近一个“市场进入与收益判断平台”，用于把原始市场数据翻译成更可读的业务结论、收益边界和工程信号。

### 1.2 项目想解决什么问题

从业务角度，这个项目主要解决四类问题：

- 市场观察：不同区域、不同年份、不同市场的价格结构、负价分布和波动形态如何
- 信号判断：当前是否存在套利窗口、FCAS 机会、电网风险或结构性事件
- 收益估算：在一组给定假设下，BESS 的套利、FCAS 和投资回报大致处于什么区间
- 数据产品化：把原始外部市场数据转成可查询、可展示、可复核、可部署的内部分析资产

### 1.3 当前真实边界

当前系统可以稳定承担的事情：

- 历史价格、事件和规则型预测的可视化与解释
- 面向 BESS 的机会分析、粗粒度收益估算和财务情景分析
- Fingrid 单数据集的同步、聚合、摘要、图表和导出
- 单机 SQLite + Redis 组合下的本地和轻量部署

当前系统不应被当成的东西：

- 生产级自动下单系统
- 多市场联合最优调度系统
- 经审计的投资决策引擎
- 对未来价格进行高置信度机器学习预测的系统

## 3. 系统总体架构

### 3.1 业务理解

系统整体上是一个“四层结构”：

1. 外部数据源层  
   AEMO、WEM、Fingrid 与相关公开数据源
2. 采集与存储层  
   脚本将数据抓取到本地 SQLite，部分热点接口配 Redis 缓存
3. 分析服务层  
   FastAPI 将原始数据转成面向图表和业务分析的 API 结果
4. 展示与交互层  
   React 前端按模块消费 API，形成主工作台和独立页面

### 3.2 工程实现

主要数据流如下：

1. `scrapers/` 脚本从外部抓取数据
2. `backend/database.py` 管理表结构、写入和读取
3. `backend/server.py` 暴露 API
4. 前端通过 `fetch` 请求 `/api/*`
5. 组件按业务模块展示结果
6. 高频接口使用 Redis 做响应缓存
7. 后端内置调度器可以定时触发市场同步与 Fingrid 增量同步

## 4. 数据源与采集链路

## 4.1 澳洲市场数据

### NEM

来源：

- AEMO NEM 历史价格归档
- NEM FCAS 相关价格字段

主要脚本：

- `scrapers/aemo_nem_scraper.py`

输出特点：

- 以年分表形式写入 `trading_price_YYYY`
- 除能量价外，还包含 NEM FCAS 价格列

### WEM

来源：

- WEM Reference Trading Price
- WEM dispatch solution 派生出的 ESS slim 数据

主要脚本：

- `scrapers/aemo_wem_scraper.py`
- `scrapers/aemo_wem_ess_scraper.py`

输出特点：

- WEM 能量价写入 `trading_price_YYYY`，区域标识为 `WEM`
- WEM ESS slim 写入独立表，而不是复用 NEM FCAS 结构

### 电网事件

来源：

- 市场公告、停运信息、调度相关事件源

主要脚本：

- `scrapers/aemo_grid_event_scraper.py`

用途：

- 为 `event-overlays` 和 `grid-forecast` 提供解释层与风险驱动

## 4.2 Fingrid 数据

来源：

- Fingrid Open Data API

主要脚本：

- `scrapers/fingrid_sync.py`

后端支持：

- `backend/fingrid/client.py`：HTTP 客户端
- `backend/fingrid/service.py`：同步编排、查询、聚合
- `backend/fingrid/catalog.py`：支持的数据集目录

当前 README 中重点示例是 dataset `317`。

## 4.3 采集策略与现实约束

- 澳洲市场数据以本地持久化为主，适合做离线分析和增量更新
- Fingrid 依赖 API key，且存在节流、超时和时间窗限制
- WEM ESS 当前是 slim 表路线，强调轻量预览而非全量市场还原
- 该项目的数据采集设计重点在“可维护”和“可部署”，而不是全量历史仓库重建

## 5. 数据库存储与表结构

### 5.1 存储总览

项目当前核心存储是 SQLite，本地主文件通常位于：

- `data/aemo_data.db`

它承载三类数据：

- 市场原始 / 半原始时序数据
- 分析缓存与同步状态
- Fingrid 数据目录与时序数据

### 5.2 澳洲市场主价格表

结构特点：

- `trading_price_2022`
- `trading_price_2023`
- `trading_price_2024`
- `trading_price_2025`
- `trading_price_2026`

设计含义：

- 按年分表，降低单表规模压力
- NEM 和 WEM 共用主价格表体系，但通过 `region_id` 区分市场
- NEM 表含 FCAS 字段，WEM 同表行则主要承载能量价

### 5.3 WEM ESS slim 表

当前 WEM ESS 相关表包括：

- `wem_ess_market_price`
- `wem_ess_constraint_summary`
- `wem_ess_capability`

设计含义：

- 不追求保存原始超大 JSON
- 只保留 FCAS 预览、约束和能力分析必需的瘦字段
- 主要服务于 WEM FCAS 分析和 WEM 预测能力

### 5.4 事件与预测相关表

- `grid_event_raw`
- `grid_event_state`
- `grid_event_sync_state`
- `grid_forecast_snapshot`
- `grid_forecast_sync_state`

设计作用：

- 事件归一化与状态化
- 预测快照缓存
- 同步状态追踪

### 5.5 Fingrid 相关表

- `fingrid_dataset_catalog`
- `fingrid_timeseries`
- `fingrid_sync_state`

设计作用：

- 保存支持的数据集目录
- 保存时序数据
- 保存同步进度、错误和覆盖范围

### 5.6 分析缓存与系统状态

- `analysis_cache`
- `system_status`

说明：

- `analysis_cache` 用于投资分析等较重计算的结果复用
- `system_status` 用于记录系统级状态，例如最后更新时间

### 5.6.1 数据质量快照与问题表

- `data_quality_snapshot`
- `data_quality_issue`

设计作用：

- 以市场维度保存最近一次可解释的数据质量快照，而不是把质量判断散落在前端或临时脚本里
- 将问题明细标准化入库，便于 `/api/data-quality/issues` 直接查询和筛选
- 为后续补齐真实采集器、调度任务和质量中心看板预留统一存储契约

### 5.7 关键字段级说明

#### `trading_price_YYYY`

- `settlement_date`：结算时间

- `lower6sec_rrp`
- `lower60sec_rrp`
- `lower5min_rrp`
- `lowerreg_rrp`

业务含义：

- 这个表是澳洲主工作台的时序底座
- 价格趋势、峰谷套利、小时剖面、NEM FCAS 分析都依赖它

#### `wem_ess_market_price`

核心字段分组：

  - `energy_price`
  - `regulation_raise_price`
  - `regulation_lower_price`
  - `contingency_raise_price`
  - `contingency_lower_price`
  - `rocof_price`
- 可用量字段：
  - `available_regulation_raise`
  - `available_regulation_lower`
  - `available_contingency_raise`
  - `available_contingency_lower`
  - `available_rocof`
- 在服量字段：
  - `in_service_regulation_raise`
  - `in_service_regulation_lower`
  - `in_service_contingency_raise`
  - `in_service_contingency_lower`
  - `in_service_rocof`
- 需求字段：
  - `requirement_regulation_raise`
  - `requirement_regulation_lower`
  - `requirement_contingency_raise`
  - `requirement_contingency_lower`
  - `requirement_rocof`
- 缺口字段：
  - `shortfall_regulation_raise`
  - `shortfall_regulation_lower`
  - `shortfall_contingency_raise`
  - `shortfall_contingency_lower`
  - `shortfall_rocof`
- 出清量字段：
  - `dispatch_total_regulation_raise`
  - `dispatch_total_regulation_lower`
  - `dispatch_total_contingency_raise`
  - `dispatch_total_contingency_lower`
  - `dispatch_total_rocof`

  - `capped_regulation_raise`
  - `capped_regulation_lower`
  - `capped_contingency_raise`
  - `capped_contingency_lower`
  - `capped_rocof`

业务含义：

- 这是 WEM FCAS preview 与 WEM 预测的关键数据表
- 它不是完整市场仓库，而是分析导向的 slim 表

#### `wem_ess_constraint_summary`

核心字段：

- `binding_count`
- `near_binding_count`
- `binding_max_shadow_price`
- `near_binding_max_shadow_price`
- `max_formulation_shadow_price`
- `max_facility_shadow_price`
- `max_network_shadow_price`
- `max_generic_shadow_price`

业务含义：

- 反映约束紧张程度
- 主要服务于事件解释和 WEM 预测信号

#### `wem_ess_capability`

核心字段：

- `facility_code`
- `participant_code`
- `participant_name`
- `facility_class`
- 各服务 `max_accredited_*`
- `facility_speed_factor`
- `rocof_ride_through_capability`
- `extracted_at`

业务含义：

- 描述参与者或设施的能力边界
- 更偏静态元数据，不是主时序分析底座

#### `grid_event_raw` 与 `grid_event_state`

`grid_event_raw` 保存原始事件事实，`grid_event_state` 保存归一化后的状态判断。  
前者更像证据库，后者更像前端与预测引擎可直接消费的解释层。

#### `fingrid_dataset_catalog` / `fingrid_timeseries` / `fingrid_sync_state`

- `dataset_catalog`：定义支持的数据集、单位、启用状态和来源
- `timeseries`：保存标准化后的时序值
- `sync_state`：保存上次同步时间、错误、窗口和覆盖度

这三张表共同构成 Fingrid 子系统的最小闭环。

## 6.2 澳洲主工作台 API

当前接口虽然仍保留历史兼容路由，但产品语义已经收敛成 3 条主链能力：

1. `Current Market`
2. `24h Outlook`
3. `BESS Decision`

当前路由包括：

- `GET /api/summary`
- `GET /api/years`
- `GET /api/network-fees`
- `GET /api/price-trend`
- `GET /api/peak-analysis`
- `GET /api/hourly-price-profile`
- `GET /api/fcas-analysis`
- `GET /api/event-overlays`
- `GET /api/grid-forecast`
- `GET /api/grid-forecast/coverage`
- `POST /api/investment-analysis`
- `POST /api/sync_data`

### 核心接口作用

- 主链接口
  - `summary`：整体数据摘要和更新时间
  - `years`：可用年份
  - `price-trend`：`Current Market` 的价格真相底座
  - `grid-forecast`：`24h Outlook` 主接口
  - `grid-forecast/coverage`：`24h Outlook` 的覆盖质量摘要
  - `investment-analysis`：`BESS Decision` 内的长期资本判断接口
- 主链内部支撑接口
  - `network-fees`：价差/成本解释所需的默认费率
  - `peak-analysis`：charge/discharge window 与 spread 支撑层
  - `hourly-price-profile`：日内结构支撑层
  - `fcas-analysis`：`Reserve Opportunity` 支撑层；NEM 更接近历史价格分析，WEM 更接近 ESS preview
  - `event-overlays`：事件解释层
  - `sync_data`：手动触发市场同步

## 6.3 Fingrid API

当前路由包括：

- `GET /api/fingrid/datasets`
- `GET /api/fingrid/datasets/{dataset_id}/status`
- `POST /api/fingrid/datasets/{dataset_id}/sync`
- `GET /api/fingrid/datasets/{dataset_id}/series`
- `GET /api/fingrid/datasets/{dataset_id}/summary`
- `GET /api/fingrid/datasets/{dataset_id}/export`

这说明 Fingrid 在工程上已经不是“附属脚本”，而是完整的独立数据产品子系统。

### 数据质量中心 API

当前新增的横向数据质量接口包括：

- `POST /api/data-quality/refresh`
- `GET /api/data-quality/summary`
- `GET /api/data-quality/markets`
- `GET /api/data-quality/issues`

它们的定位不是替代业务分析接口，而是给系统增加一层“数据是否可靠、覆盖是否完整、当前结论应如何标注”的统一出口。

## 6.4 接口风格

统一特征：

- 以 JSON 为主
- 大部分接口围绕前端图表消费设计
- 兼顾业务摘要字段与原始时序字段
- 关键分析接口开始统一返回 `metadata`，用于表达 `freshness`、`source_version`、`timezone`、`interval_minutes`、`quality_grade` 与 `coverage`
- 重点接口带缓存
- 错误响应多为 HTTPException 包装后的 4xx / 5xx

### 6.7 主接口处理链路

这一节不是重复接口定义，而是说明“一个请求进来之后，系统实际按什么顺序处理”。

#### `/api/price-trend` 请求生命周期

1. 前端带上 `year`、`region`、可选 `month/quarter/weekend_only/workday_only/limit` 发起请求。
2. 后端根据 `year` 定位到 `trading_price_YYYY` 表。
3. 组装 SQL 条件，按区域和时间切片过滤价格序列。
4. 从数据库取出时序行后，计算基础统计值：
   - 最小值
   - 最大值
   - 平均值
   - 负价占比
   - 样本数
5. 如果点数超过 `limit`，优先走 `lttbc` 做 LTTB 降采样。
6. 如果 `lttbc` 或 `numpy` 不可用、运行报错，自动降级到均匀抽样，不阻断接口返回。
7. 返回图表序列和顶部 KPI。

这条链路说明一个重要事实：`price-trend` 的核心不是“复杂模型”，而是“数据库过滤 + 统计摘要 + 可视化友好的采样”。

#### `/api/peak-analysis` 请求生命周期

1. 接收市场、区域、年份、聚合粒度以及网络费参数。
2. 从年度价格表提取原始序列。
3. 按 1h / 2h / 4h / 6h 等窗口重组价格。
4. 计算每个窗口的：
   - 充电均价
   - 放电均价
   - 毛价差
   - 扣除网络费后的净价差
5. 生成分布、排序、阈值判断和代表性窗口。
6. 结果同时被 `SpikeProfitAnalysis`、`CoOptimizedBacktest` 等前端模块复用。

#### `/api/fcas-analysis` 请求生命周期

1. 根据市场分流到 NEM 或 WEM 分支。
2. NEM 分支直接读取年度价格表中的 FCAS 字段。
3. WEM 分支读取 `wem_ess_market_price` 为主，必要时联动约束/能力信息补充解释。
4. 生成服务拆分、小时分布、趋势线和汇总统计。
5. 返回给 `FcasCollapseForecaster`（Stage 4）和 `CapacityCreditsAnalysis`（WEM）。

#### `/api/grid-forecast` 请求生命周期

1. 接收 `market`、`region`、`horizon`、`as_of`。
2. 先尝试从 `grid_forecast_snapshot` 读取对应快照。
3. 若无合适缓存，则从事件状态、近端价格、WEM slim / NEM 历史等上游源重建预测输入。
4. 进入 `grid_forecast.py` 的规则引擎。
5. 产出：
   - `summary`
   - `windows`
   - `drivers`
   - `coverage/confidence` 类元数据
6. 结果写回快照表，供后续相同请求复用。

#### `/api/investment-analysis` 请求生命周期

1. 前端提交完整 `InvestmentParams`。
2. 后端先做 Pydantic 参数校验。
3. 生成分析请求键，检查 `analysis_cache` 中是否已有相同输入结果。
4. 若命中缓存，直接返回，避免重复重算。
5. 若未命中：
   - 读取套利和 FCAS 相关基础收益口径
   - 进入 `backend/engines` 财务模型链
   - 计算现金流、回收期、IRR、ROI、NPV、敏感性和蒙特卡洛结果
6. 将结果写入 `analysis_cache`。
7. 返回给前端投资分析模块。

#### Fingrid `/series` 与 `/summary` 请求生命周期

1. 路由先校验数据集是否存在于 catalog。
2. 由 `fingrid_service` 统一处理时区、聚合粒度、时间窗口。
3. 从 `fingrid_timeseries` 拉取原始行。
4. `series` 路径负责原始或聚合时序输出。
5. `summary` 路径在此基础上继续计算均值、峰值、谷值、分布等摘要。
6. 前端再决定卡片、折线、分布面板怎么展示。

## 8. 核心算法与模型逐层解析

## 8.1 Current Market 真相层

业务理解：

- 用于回答“现在是什么市场”
- 重点看价格状态、极值、负价分布、regime 和数据可信度

工程实现：

- 后端从 `trading_price_YYYY` 取时序
- 在点数过多时做下采样
- 同时给出最小值、最大值、均值、负价比例等统计
- 通过事件层与 regime 层补足“为什么当前像这样的市场”

这一层在前端上的主要呈现对象包括价格主图、summary、regime、数据质量和必要的日内结构视图。

## 8.2 24h Outlook 支撑层之一：Charge / Discharge Window

业务理解：

- 不是“真实调度执行收益”，而是为未来 24 小时窗口判断提供理论价差线索

工程实现：

- 基于不同结算粒度生成 1h / 2h / 4h / 6h 窗口
- 计算 gross / net spread
- WEM 和 NEM 因结算粒度不同而走不同窗口点数

## 8.3 BESS Decision 支撑层之一：Reserve Opportunity

业务理解：

- NEM 更接近历史价格分析
- WEM 更接近基于 slim 表的 preview 估算
- 这一层当前是机会代理层，不应被读成完整联合收益真相

工程实现：

- NEM 依赖主价格表中的 FCAS 列
- WEM 依赖独立 WEM ESS slim 表
- 二者在实现和可信边界上不是对称关系

## 8.4 跨主线解释层：事件层

业务理解：

- 不是单纯列出新闻，而是把事件归一化成对主链判断更有意义的状态标签

工程实现：

- `grid_events.py` 负责事件归类、影响域映射和时间过滤
- 下游既服务 `Current Market` 图表解释，也服务 `24h Outlook` 预测引擎

## 8.5 24h Outlook 主判断层

业务理解：

- 是规则型信号引擎，不是 ML 模型
- 输出的是未来 24 小时的风险和机会判断，而不是价格精确预测
- 当前它是澳洲主线里承上启下的一层：把市场真相翻译成未来窗口判断，再把判断送进 BESS 决策链

工程实现：

- `grid_forecast.py` 负责 NEM / WEM 分支
- NEM 与 WEM 使用不同输入与输出可信度
- `grid-forecast/coverage` 单独输出覆盖质量摘要

### 8.5.1 2026-05 澳洲预测层收敛改造

2026 年 5 月这一轮改造，核心不是“把预测做得更复杂”，而是把原本偏价格形态驱动的链路收敛成更贴近电力市场基本面的结构。

这次改造后的主判断框架是五组因子：

- `supply`：供给侧可用性、主要机组停运、维护集中度
- `demand`：短期负荷压力、天气/工业负荷冲击、结构性负荷增长
- `network`：主网约束、联络线压力、区域分离风险
- `reserve`：备用紧张、短缺风险、FCAS 机会
- `calibration`：近端价格、负价比例、近期 FCAS 均价，只作为校准项而不是主驱动

这一轮明确做了几件事：

- NEM `24h` 预测从“最近价格形态外推”改成“predispatch + supply/demand/network/reserve”主导。
- NEM `7d` 与 `30d` 彻底拆开：`7d` 看运营型供需与 outage/network/reserve，`30d` 看结构性供给可用率、维护集中度与结构性负荷增长。
- WEM 已完成真实数据接入，把 `binding_count / shadow price / shortfall / reserve pressure` 放回核心，能量价格和 5 种 ESS 辅助服务均有实际数据支撑。
- P1 regime layer 仍保留原有字段契约，但内部权重已经下调 `latest_price / spike_ratio / negative_ratio / price_separation` 的主导性，避免旧价格逻辑重新污染 P2。

### 8.5.2 NEM 与 WEM 当前真实口径

#### NEM

- `24h` 更像运营视角的短期风险识别。
- `7d` 更像周度 regime outlook，不是逐时价格预测。
- `30d` 更像结构性供需观察，不是 forward curve 替代品。
- `market_context` 里新增了一组基本面摘要字段，例如：
  - `dominant_supply_availability_delta`
  - `major_generation_outage_score`
  - `major_network_outage_score`
  - `interconnector_stress_score`
  - `weather_load_stress_score`
  - `demand_level_vs_normal`
  - `reserve_pressure_score`

#### WEM

- 已完成真实数据接入，不再是 preview-grade。
- 能量价格（Reference Trading Price）和 5 种 ESS 辅助服务均有实际数据，约束紧张度、缺口与设施能力数据也已入库。
- 更适合看约束、短缺、备用和安全压力，投资级长周期分析仍需更长历史数据积累。

### 8.5.3 第二轮检修结论

在 2026 年 5 月 8 日至 2026 年 5 月 10 日的第二轮检修里，又专门修正了 3 个容易让口径漂移的点：

- 低置信度事件不再通过“事件数量加分”堆出高压力分；事件计数加权已经按 `confidence` 收敛。
- NEM `7d/30d` 的 `negative_price_risk_score` 去掉了无信号硬底噪，没有负价信号时会诚实回到低位。
- 长周期 `demand_level_vs_normal` 不再拿事件压力分伪装成负荷偏离，而是优先使用最近 `operational_demand_actual_hh` 的真实负荷序列估算 baseline；没有数据时回落到保守值。

这 3 个修正的意义在于：现在同一个字段在不同 horizon 上的语义更稳定，预测分数也更不容易被噪声事件和历史价格残影带偏。

### 8.5.4 这一层明确不做什么

- 不把 `grid-forecast` 包装成 bidding strategy。
- 不把 forecast 自动升级成 investment 结论。
- 不把 futures / forwards 当作默认核心因子。
- 就算未来引入 forward 信号，也必须先经过成交量和流动性闸门，否则不应进入主判断链路。

## 8.6 BESS Decision 长期资本判断层

业务理解：

- 这是一个“带明确假设的财务情景模型”
- 不等于资产历史真实收益复盘
- 当前产品语义上，它属于 `BESS Decision` 内的 `Investment Readiness`，不是独立一级主舞台

工程实现：

- `POST /api/investment-analysis`
- 参数模型位于 `backend/models/financial_params.py`
- 财务计算位于 `backend/engines/financial_model.py`
- 同时结合套利、FCAS、折现、衰减、债务容量、杠杆 IRR 等要素

## 8.7 BESS Decision 底层引擎

相关模块：

- `bess_backtest.py`
- `engines/battery_model.py`
- `engines/dispatch_optimizer.py`
- `engines/revenue_model.py`

它们共同承担：

- 储能物理约束建模
- 调度 / 收益估算
- 财务输入生成
- 支撑 `Primary Call -> Why This Call -> Economics And Boundary` 这一条决策表达链

### 8.8 引擎层职责拆分

#### `battery_model.py`

- 负责电池衰减、寿命、增强策略等物理状态演化

#### `dispatch_optimizer.py`

- 负责调度优化逻辑
- 更偏“给定价格路径下的最优行为近似”

#### `revenue_model.py`

- 负责收益侧估算，尤其是套利与 FCAS 的组合口径

#### `financial_model.py`

- 负责 NPV、IRR、ROI、Payback、Debt Capacity、Levered IRR 等财务计算

#### `market_adapter.py`

- 负责把市场数据查询抽象成分析可消费的接口

它们的存在说明投资分析并不是一坨写死在 `server.py` 里的公式，而是已经拆成多个可演进的责任单元。

## 9. 业务口径、结果解释与适用边界

### 9.1 读结果时必须记住的事情

- 价格分析不等于收益分析
- 理论套利机会不等于真实可执行收益
- WEM 已接入真实数据，但历史深度不及 NEM，长周期投资级结论仍需积累
- `metadata.quality_grade` 如果是 `preview` 或 `analytical-preview`，应理解为“可用于方向分析”，而不是“已完成严谨数据审计”
- 投资分析是模型结果，不是历史已实现现金流
- 预测模块是规则信号，不是 ML 点预测

### 9.2 NEM 与 WEM 的关系

NEM 和 WEM 均已接入真实市场数据，但两者仍存在差异：

- NEM 历史口径更深，FCAS 10 种服务完整覆盖
- WEM 已接入能量价格和 5 种 ESS 服务真实数据，含约束摘要与设施能力
- WEM 历史深度不及 NEM，长周期投资分析能力仍需积累
- 两者在结算粒度（NEM 5分钟 vs WEM 30分钟）和市场结构上存在本质差异

### 9.3 Fingrid 的边界

Fingrid 当前更像独立数据分析页，不和澳洲主工作台共享一套业务模型。  
它已形成自己的采集、聚合、摘要和导出路径，但尚未和 BESS 财务模型深度耦合。

## 10.5 同步任务逐过程拆解

### `run_sync_scrapers`

这是澳洲市场主同步任务，顺序非常明确：

1. 获取市场同步锁，避免重复任务重叠执行。
2. 计算最近两周时间窗。
3. 执行 `aemo_wem_scraper.py`，补近 14 天 WEM 价格。
4. 执行 `aemo_wem_ess_scraper.py`，补近 30 天 WEM ESS slim 数据。
5. 执行 `aemo_nem_scraper.py`，补近两周所在月份的 NEM 数据，并带 FCAS。
6. 执行 `aemo_grid_event_scraper.py`，补近 180 天事件。
7. 写入 `last_update_time`。
8. 释放锁。

从这个顺序可以看出，它是一个“多脚本编排器”，不是一个单 SQL/单模块同步器。

### `run_fingrid_dataset_sync`

这是 Fingrid 单数据集同步入口：

1. 先检查 `FINGRID_API_KEY` 是否配置。
2. 获取 Fingrid 同步锁。
3. 调 `fingrid_service.sync_dataset(...)`。
4. 成功时返回 `dataset_id / mode / records_upserted / last_synced_timestamp_utc`。
5. 失败时返回结构化错误对象，而不是只打日志。
6. 最终释放锁。

### `fingrid_service.sync_dataset`

这是 Fingrid 同步真正的核心过程：

1. 从 catalog 读取数据集配置。
2. 如果是 `backfill`，使用配置中的默认起始时间；如果是 `incremental`，使用默认回看天数。
3. 将时间窗切成按月窗口，避免一次拉太大范围。
4. 每个窗口调用 Fingrid API。
5. 每条原始行经过 `normalize_fingrid_row` 标准化。
6. 写入 `fingrid_timeseries`。
7. 更新 `fingrid_sync_state` 为 `running`、`ok` 或 `error`。

这说明 Fingrid 不是“抓完直接展示”，而是“先标准化入库，再以统一查询接口提供数据服务”。

### `run_fingrid_hourly_sync`

1. 先检查 API Key。
2. 获取全局 Fingrid 同步锁。
3. 遍历 catalog 中所有支持的数据集。
4. 对每个数据集跑一次 `incremental` 同步。
5. 汇总成功数、失败数和失败明细。
6. 返回结构化结果供日志或状态面板消费。

## 10.6 锁、缓存与并发边界

### 锁机制

- 市场同步和 Fingrid 同步使用不同的 job lock 名称。
- 锁的目标不是“提升性能”，而是防止重复抓取、重复写库和状态污染。
- 手动触发接口在拿不到锁时会直接返回冲突或 `skipped`，而不是排队无限等待。

### Redis 响应缓存

- `response_cache.py` 封装了 `RedisResponseCache`。
- Redis 不可达、依赖未安装、超时等情况不会让接口整体失败。
- 失败时行为是：
  - 记录 warning
  - 将内部 client 清空
  - 本次请求退化为无缓存直算

### SQLite 并发边界

- 当前项目是 SQLite 架构，适合单机部署、轻中度并发和分析型查询。
- 它不适合高频写入和多实例共享写竞争。
- 同步任务、快照写入、分析缓存写入都在争用同一个本地数据库文件时，要关注锁等待和 I/O 抖动。

## 13. 当前限制、风险点与非目标

### 13.1 文档层面

- 历史分析、审计、需求和现状文档并存，容易互相冲突
- 旧文档里仍有过时接口名、表名和历史结论

### 13.2 数据与算法层面

- WEM 与 NEM 的能力并不对称（WEM 历史深度不及 NEM）
- WEM 已完成真实数据接入（能量价格 + 5 种 ESS 服务 + 约束 + 能力），但长周期投资分析仍需更多历史积累
- 数据质量中心 v1 已经补上了统一快照、问题表和最小 collector，当前可直接从 NEM 年度价格表、WEM ESS slim 表、Fingrid 同步状态与时序表生成质量快照
- `price-trend` 与 Fingrid 状态虽然已经统一输出 `metadata`，但这不代表所有历史接口都完成了同样粒度的结果治理
- `Investment Readiness` 依赖模型假设，不是已实现收益
- `24h Outlook` 是规则引擎，不是机器学习价格预测
- `Reserve Opportunity` 当前仍是机会代理层，不是完整联合收益真相

### 13.3 工程层面

- SQLite 适合单机和轻量部署，但不适合高并发多写场景
- Redis 不可用时系统会退化为无缓存路径
- 内置调度器在多副本部署时需要显式控制

### 13.4 产品层面

- 澳洲主工作台与 Fingrid 页面目前仍是两条产品线
- 还没有统一成跨市场、跨区域、跨收入口径的单一分析框架
- 澳洲主工作台内部虽然已经收敛成 `Truth -> Forecast -> Decision`，但历史组件和历史文档仍可能残留旧并列模块语义
- WEM 已完成真实数据接入，NEM/WEM 双市场分析能力已形成，但部分代码层 metadata 标记（preview_only）尚未完全清理

### 13.5 运行时故障模式与排障入口

#### `price-trend` 500 或图表空白

优先排查：

1. 对应年份的 `trading_price_YYYY` 是否存在。
2. 目标 `region` 在该年份表中是否有数据。
3. 是否传入了过严的月份/季度/工作日过滤导致结果集为空。
4. 若点数很多，观察日志里是否出现 LTTB 降级 warning。

注意：LTTB 降级本身通常不会导致接口失败，它更多影响的是采样质量，不是可用性。

这类故障在产品语义上首先影响的是 `Current Market` 真相层；如果这一层失真，后续 `24h Outlook` 和 `BESS Decision` 的阅读链也会一起失去锚点。

#### Fingrid 页面无数据

优先排查：

1. `FINGRID_API_KEY` 是否配置。
2. `fingrid_sync_state` 是否长期停留在 `error`。
3. `fingrid_timeseries` 是否已有该 `dataset_id` 数据。
4. 请求时间窗是否超出已同步覆盖范围。

#### 手动同步无响应或返回冲突

优先排查：

1. 是否已有同步任务处于运行态。
2. Redis / SQLite 锁竞争是否导致状态回写延迟。
3. 定时调度器与手动触发是否在同一时间窗内重叠。

#### `grid-forecast` 空态或结果明显异常

优先排查：

1. `grid_forecast_snapshot` 是否已有该区域与 horizon 的最近快照。
2. `grid_event_state` 是否为空，导致驱动因子解释层缺失。
3. WEM 是否被误按 NEM 口径理解；WEM 当前仍是 `preview/core-only`。
4. 是否把 `7d/30d` 误当成逐时价格预测读取。

注意：这类问题首先影响的是 `24h Outlook` 主判断层，不一定意味着底层价格数据坏掉，更常见的是 horizon 语义被误读或预测覆盖不足。

#### `investment-analysis` 过慢或结论波动大

优先排查：

1. 输入参数是否发生较大变化，例如成本、寿命、贴现率、杠杆或收益假设。
2. `analysis_cache` 是否命中；未命中时会走更重的财务计算路径。
3. 上游套利 / FCAS 收益口径是否刚被刷新，导致长期资本判断重新计算。
4. 是否把它误当成“已实现收益复盘”；它当前本质上仍是 `Investment Readiness` 情景模型。

注意：这类问题属于 `BESS Decision` 的长期资本判断层，波动并不一定代表 bug，也可能只是模型假设变化被诚实反映出来。

1. 是否已有后台同步任务在运行。
2. 系统锁是否未正常释放。
3. SQLite 是否被长事务占用。

#### 投资分析过慢

优先排查：

1. 相同参数是否命中 `analysis_cache`。
2. 是否开启了敏感性 / 蒙特卡洛并设置了较大迭代数。
3. 是否在资源较小的容器中运行导致 CPU 计算变慢。

#### Redis 不可用

预期行为：

- 不应造成整体服务启动失败。
- 接口会退化为无响应缓存模式。
- 影响主要体现在重复请求延迟上升，而不是功能缺失。

## 15. 澳洲主线术语对照

为了避免继续用历史组件名直接替代产品语义，当前更推荐按下面这组词来理解澳洲主线：

- `Current Market`
  - 指当前市场真相层，核心回答“现在是什么市场”。
- `24h Outlook`
  - 指未来 24 小时判断层，核心回答“接下来更像什么市场”。
- `BESS Decision`
  - 指储能行动与资本判断层，核心回答“现在该怎么做、值不值得做”。
- `Reserve Opportunity`
  - 对应历史上的 FCAS analysis 产品口径，但当前应理解为机会代理层，而不是完整联合收益真相。
- `Charge / Discharge Window`
  - 对应历史上的 peak analysis / charging window 相关能力，当前属于 `24h Outlook` 的窗口判断支撑层。
- `Revenue Breakdown`
  - 对应历史上的 revenue stacking，更强调“收益来自哪里”。
- `Investment Readiness`
  - 对应历史上的 investment analysis，但当前应理解为 `BESS Decision` 内的长期资本判断层。
- `Decision Diagnostics`
  - 指模拟器、循环成本、报告预览等诊断层；可访问，但不再承担首页主建议角色。
- `preview`
  - 可用于方向判断或预览，不应直接被读成投资级结论。
- `core-only`
  - 只覆盖核心能力，不代表完整市场覆盖。
- `decision-grade`
  - 可用于运行判断或配置判断，但仍不等于自动交易执行授权。

这组术语的核心目的，是把页面阅读顺序重新固定到：

`Truth -> Forecast -> Decision`

而不是重新滑回“价格图 / FCAS / 投资分析 / 模拟器”这种历史并列模块视角。
