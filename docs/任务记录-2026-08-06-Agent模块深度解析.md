```
前端 (Web)
   │  POST /api/v1/agent/run | run-async | chat-stream (SSE) | tools | workflows | history
   ▼
routes/agent_routes.py  ── JWT 鉴权 (access_control) ── Redis/内存任务存储 ── agent_execution_log 落库

AgentOrchestrator (orchestrator.py, 单例)

   ├── ReAct 循环（run_stream，最多 15 步，总超时 180s）
   │     LLMAdapter.chat_stream_events → 解析 tool_calls → 并行执行 → 结果回灌 messages
   ├── ToolRegistry.execute（超时守卫 + TIMEOUT/ERROR 归类）

   ├── SessionMemory（会话记忆注入 system message，版本感知）
   └── synthesize_report（LLM 综合 → 失败回落规则综合）
         └── AgentReport（执行摘要/阶段结果/建议/置信度/风险标记/数据质量说明）
```

### 1.3 类设计要点

- **`AgentOrchestrator`**：无状态执行 + 单例工厂 `get_orchestrator()`。持有 `LLMAdapter`、`ToolRegistry`、`SessionMemory` 三个依赖，全部以单例注入。
- **`ToolRegistry`**：`register(definition, executor)` 分离"LLM 可见的 schema"与"Python 执行器"；`execute()` 统一做超时（`asyncio.wait`）、异常归类（TIMEOUT/ERROR）、计时。同步执行器自动经 `run_in_executor` 放入线程池，避免阻塞事件循环。
- **`ToolResult.to_llm_message()`**：回灌 LLM 的结构化摘要（非暴力截断）——大数组取 length+前 3 样本、深 dict 采样 8 键、数值保留，上限 3000 字符；这是 P1"统一截断路径"的落点。
- **枚举体系**：`ToolStatus(success/error/timeout)`、`WorkflowStatus(running/completed/partial/failed)`、`ConfidenceLevel(high/medium/low)`、`MarketType(NEM/WEM)`。

## 2. 核心功能梳理

### 2.1 双模执行 + 四层降级（orchestrator.py `run` / `run_stream`）

1. **模板模式**（确定性）：`workflow_template_id` 显式指定时直连模板；按 `parallel_groups` 分组 `asyncio.gather` 并行执行。
2. **ReAct 模式**（LLM 驱动）：仅当 `health_check()` **真实探测**通过才进入（config-only 的 `is_available()` 不足以进入，这是 P0 修复点）。
3. **降级链**：LLM 不可用 → `match_workflow_from_query` 关键词匹配模板 → 命中失败 → 默认 `quick_market_overview` → 综合阶段再降级到规则综合。降级原因写入 `report.metadata["llm_degraded"/"llm_degraded_reason"]`。

### 2.2 ReAct 循环（`run_stream`，SSE 主路径）

```python
for step_num in range(1, self.max_steps + 1):           # 默认 15 步
    if elapsed > self.total_timeout: break              # 默认 180s 总预算
    async for ev in self.llm.chat_stream_events(messages, openai_tools):
        ...                                              # 流式 token + 累积 tool_call 片段
    if not tool_calls:                                   # 无工具调用 = 最终答案
        final_answer_given = True; break
    # 参数合并：LLM 参数 + context.region/year + params_override
    raw_results = await asyncio.gather(*[_exec_one(i) ...])   # 并行执行 + 自适应重试
    messages.append(result.to_llm_message())             # 结构化摘要回灌
```

SSE 事件分类学：`start / status / plan / token / reflection / tool_call / tool_result / answer_end / report / error / done`。

### 2.3 组件关系

| 组件 | 上游 | 下游 |
|---|---|---|
| `agent_routes` | 前端 HTTP/SSE | orchestrator、tool registry、DB（执行日志） |
| `orchestrator` | routes | llm_adapter、tools、workflows、synthesizer、session |
| `tools` | orchestrator | engines/*、models/*、deps.get_db、data/ JSON |
| `synthesizer` | orchestrator | llm_adapter、tool_contracts、prompts |

## 3. 实现机制解读

### 3.1 工具执行与超时预算（`ToolRegistry.execute`）

- 同步执行器走 `loop.run_in_executor`；用 `asyncio.wait(timeout=...)` 而非裸 `wait_for`，超时后显式 `task.cancel()` 防线程泄漏。
- 超时归类为 `ToolStatus.TIMEOUT`（区别于 ERROR），供综合器降低置信度。
- 重工具专属预算（`_HEAVY_TOOL_TIMEOUTS`，P0 修复产物）：`market_screening`/`regional_ranking`/`co_optimized_backtest` = 90s，`investment_analysis` = 60s，其余默认 30s。

### 3.2 三级缓存

1. **工具级会话缓存**（orchestrator）：仅 4 个纯读工具（`data_quality_check`、`price_trend_analysis`、`saturation_check`、`market_screening`），键为 `tool:region:year`，TTL 300s。输出依赖额外参数（如 `window_hours`、`threshold`）的工具被刻意排除。
2. **SessionMemory**（session.py）：会话内工具结果摘要（截 500 字符），TTL 30 分钟、上限 50 条；`args + data_version` 联合 MD5 哈希——数据同步后版本号变化自动失效，防止旧缓存。注入 system message 提示"无需重复执行"。
3. **LLM 健康探测缓存**：`health_check` 结果 TTL 300s，避免每次运行都打 1-token 探测。

### 3.3 重试与自适应参数

- **LLM 层**（`_retry_with_backoff`）：指数退避 + jitter，仅重试 429/408/5xx/超时/连接错误；401/403/invalid key 快速失败不重试。
- **工具层**（`_execute_tool_with_retry`）：`enable_retry` 时最多 `max_retries+1` 次；失败后规则化调参（`_adapt_args_on_failure`）——超时则砍半 `n_simulations`/`projection_years`；无数据则回退上一年。无需 LLM 参与。

### 3.4 上下文工程

- **多轮历史预算**（P2-5）：`_trim_history` 滑窗 10 条 + 8000 字符预算，从新到旧累积，防上下文溢出。后端无状态，历史由前端持有。
- **工具结果回灌**：`to_llm_message` 结构化摘要（见 1.3），综合阶段 `_format_tool_results_for_llm` 复用同一 `_summarize_dict`（P1 统一截断路径）。
- **规划/反思**：`enable_planning` 时先让 LLM 输出 JSON 计划（`AnalysisPlan`）；`enable_reflection` 时正则解析 `[REFLECT] step=N verdict=... reason="..."` 标记透出 SSE。（注：仍是自由文本正则解析，P2 待办改 structured output。）

### 3.5 综合与置信度（synthesizer.py）

- **LLM 综合**：`SYNTHESIS_PROMPT` 约束"只用工具数据、不编造"；输出按"执行摘要/关键指标/综合建议/风险标记/数据质量说明"分段，`_extract_section` 解析。
- **规则兜底**：`_rule_based_synthesize` 确定性生成摘要与建议（NPV 正/负二分建议），规则综合**永不给 HIGH** 置信度。
- **`_infer_confidence` 算法**：成功率 ≥0.9 且关键工具（`investment_analysis`/`co_optimized_backtest`/`merchant_risk_simulate`）无失败 → HIGH；preview 数据等级封顶 MEDIUM；关键工具失败降级；LLM 文本仅作 tiebreaker。

### 3.6 推理叙事（`_build_reasoning_narrative`）

无 LLM 时也能生成逐步分析走查（各工具关键指标 + 综合判断），外层 `_safe_reasoning_narrative` 保证任何异常返回空串不崩。

- 2026-08-05 文档结论——所有基于 `run_hindsight_optimization` 的收入结论需打折（滚动回测 vs 完美前瞻差距显著）——与该工具的保守底座策略一致；`co_optimized_backtest` 仍是 MILP 后见优化，其结论解读时应注意同一偏差。
- **改进空间**：将 `scripts/backtest_rolling_predispatch.py` 的闭环滚动回测产出接入 agent 作为收入底座校准系数。

## 6. 性能特征评估

| 维度 | 现状 | 评价 |
|---|---|---|
| 并行度 | 模板 parallel_groups + ReAct 单轮多 tool_calls `asyncio.gather` | ✅ 好：11 步完整可行性分析压缩到 5 个串行波次 |
| 重工具 | market_screening 全年 5 分钟价格 ~54 万行 Python 聚合，单次 ~20s | ⚠️ P2 待办：SQL 聚合下推（当前靠 90s 超时预算规避） |
| 阻塞规避 | 同步执行器全部 `run_in_executor` 线程池 | ✅ 事件循环不阻塞 |
| 重复计算 | 4 工具会话缓存 + SessionMemory 去重提示 | ✅ 但 SessionMemory 仅"提示"不强制跳过（`has_result` 存在但未在主循环强制消费） |
| 超时分级 | 工具 30/60/90s + 总 180s + MILP 内置 30s | ✅ 三层防线，报告不会被单点拖死 |
| LLM 成本 | token 用量累加进 `report.metadata.llm_usage`（实测 ReAct 单轮 ~36k tokens） | ✅ 可见；⚠️ 单例共享，并发下 per-run 近似 |
| 扩展性 | 新工具 = `register()` 一次 + executor 一个函数；新模板 = 字典加一项 | ✅ 水平扩展成本低；⚠️ 工具数量增长会膨胀 function-calling schema（31 个已不小） |

## 9. 最佳实践建议

### 9.1 已具备、值得保持

- **双模分离**（workflow vs agent）符合 Anthropic《Building Effective Agents》"简单优先"；四层降级保证任何 LLM 故障下系统仍产出结构化报告。
- **契约常量层**是低成本高收益的防漂移手段，建议新增漂移热点工具时一律先加常量。
- **置信度推断不信任 LLM 自述**，以工具成功率/数据等级/关键工具为准——投资决策场景的正确姿态。

### 9.2 建议改进（按优先级）

1. **agent evals 黄金集进 CI**：`tests/test_agent_golden_trajectories.py` 已存在（270 行），应扩充到 20 条轨迹并挂 CI，把"真跑才算数"制度化（P2 待办 1）。
