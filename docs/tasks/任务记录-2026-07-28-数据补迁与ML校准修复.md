# 任务记录：数据补迁与 ML 校准修复（2026-07-28）

> 状态：已完成
> 关联背景：结构化质疑审查（两轮）→ 修复清单 P0② 前置诊断 → 本次修复

---

## 1. 背景

对项目做"现在到底准不准"的现状诊断时，发现 `ForwardPriceEngine.validate_against_benchmarks()` 的偏差随环境状态剧烈摆动，追查后定位到一个数据迁移缺口和两个校准引擎 bug。

## 2. 发现的问题

### 2.1 SQLite → PostgreSQL 迁移不完整（数据缺口）

| 年份 | SQLite（源） | PostgreSQL（迁移后） | 完成度 |
|---|---|---|---|
| 2020–2024 | 各 ~52.5 万行 | 各 ~52.5 万行 | 完整 |
| 2025 | 525,600 行（全年） | 17,219 行 | **仅 3%** |
| 2026 | 87,796 行（1/1–6/17） | 777 行（4/14 起，为迁移后新增量） | **基本缺失** |

### 2.2 Bug 1：校准引擎在验证集不足时放行未验证模型

`backend/engines/ml_calibration_engine.py` `_train_model()`：当验证样本 < 30 时，else 分支将 status 标为 `"calibrated"`（validation_mae=None）并保留模型 → 一组从未做过样本外检验的参数进入生产计算。

### 2.3 Bug 2：校准"failed 但生效"的僵尸状态

`backend/engines/forward_price_engine.py` `_try_ml_calibration()`：先填充 `self._calibrated_spreads`，后执行日志 `f"MAE={...:.1f}"`；当 MAE=None 时格式化崩溃跳入 except，状态标为 `failed`，**但校准值已生效**。

### 2.4 三种环境状态下同一模型的偏差表现（Modo 基准 16 点）

| 环境状态 | 偏差 | 达标数(<30%) |
|---|---|---|
| PG 未启动（校准静默失败 → 硬编码默认） | -40% ~ -66% 全线低估 | 0/16 |
| PG 启动但 2025 数据仅 3%（垃圾校准 + 僵尸 bug） | +36% ~ +182% 全线高估 | 1/16 |
| 数据补齐 + bug 修复后 | 平均绝对偏差 18.8% | **13/16** |

## 3. 修复内容

### 3.1 数据补迁（不毁已有数据）

- 方式：定向脚本 `INSERT ... ON CONFLICT (settlement_date, region_id) DO NOTHING`（幂等；不 TRUNCATE / 不 DELETE）
- 注意点：需先将自增序列拨到 `max(id)+1`（`setval`），否则新行 id 撞已有行主键
- 结果：
  - `trading_price_2025`：17,219 → **542,811 行**（全年完整）
  - `trading_price_2026`：777 → **88,573 行**（1/1–7/25，SQLite 与 PG 原有数据合并，无丢失）
- 说明：`scripts/migrate_sqlite_to_pg.py` 默认模式对已存在表执行 TRUNCATE + 全量重灌，`--only-missing` 模式则跳过已存在表——两者都不适合"补数据"场景，故未使用。

### 3.2 Bug 修复

- `ml_calibration_engine.py`：验证样本不足 → status=`insufficient_validation`，清空模型，拒绝校准，回退默认参数
- `forward_price_engine.py`：校准值先构建于临时容器，全部成功后原子性赋给实例；日志改为 None 安全格式化；except 分支清空 `_calibrated_spreads` 残留

### 3.3 修复后 ML 校准首次健康跑通

```
status=calibrated | MAE=31.7 | R²=0.57 | CI 覆盖率=0.83（目标 0.80）
训练样本=9,130（2020–2024） | 验证样本=2,120（2025-01 ~ 2026-06）
```
