## 0. 结论先行

平台在**分析能力与后端治理**上已明显超出「公测产品」的常见完成度：22 个分析模块 × 3 个市场、统一响应契约（`metadata` 含 data_grade/freshness/coverage/lineage/methodology_version）、双层 RBAC、作业框架、OpenLineage 血缘、假设登记制度、CI/CD 与可观测性。这些是通常需要数年才能建好的底座。

缺口集中在**「产品化外壳」而不是「分析内核」**，具体是四类：

| 缺口类别 | 严重度 | 一句话诊断 |
|---|---|---|
| **业务对象缺失** | 致命 | 全站没有「项目/资产」这个概念。所有分析结果都是**一次性的、无归属的、不可版本化的**。用户无法表达「我有一个 200MW/400MWh 的储能项目，我要持续跟踪它」，只能反复重跑并自己截图存档。这是本产品从「数据查看器」升级为「决策工作台」的唯一阻塞点。 |
| **自助获客链路断裂** | 致命 | 邀请制 + 匿名 bootstrap 并存，但**没有注册入口**：`/pricing` 三个 CTA 全部指向 `/login`（对无账户者是死路）；`PricingPage` 承诺的「方法论白皮书」没有对应页面；隐私页第 5 条承诺「可申请导出或删除」**没有对应端点**（属不实陈述）。 |
| **信任与法务敞口** | 高 | 产品当前名为「AEMO Intelligence」，而 AEMO 是澳洲法定市场运营机构 → **仿冒/暗示背书的法律风险**；服务条款未写法人主体、无 ABN/ACN、无管辖法域；缺 DPA/AUP/Cookie 政策；`data/financial_evidence.json` 含 Modo 等第三方数据许可未盘点。 |

7. 优先级排序 —— 以「公测期用户反馈最大化」为目标函数排批次

## 2. 维度一：业务对象审计（致命缺口）

### 2.1 现状：有「分析」无「资产」

已核实的事实：

- `web/src/lib/marketConfig.js` 定义了 7 阶段漏斗（stages，带 `dataDependencies` L74-106）与 `DEFAULT_BESS_PARAMS`（L273）。
- `data/assumptions_registry.json` 是**全局**假设登记，不是**项目级**参数。
- 数据库侧：`database.py` 的 65 张表里，与用户产出相关的只有 `saved_report`、`agent_execution_log`、`user_preference`、`analysis_cache`。**没有任何形如 `project` / `asset` / `site` 的业务实体表**。
- `analysis_cache` 是按 `data_version` 键化的**性能缓存**，不是用户资产：`data_version = db.get_last_update_time()`（`investment_routes.py:105-107`）→ **上游任何一次数据更新就让全部缓存键变更**，用户昨天看到的结果今天不复现。

### 2.2 后果（用户可感知）

| 用户真实任务 | 当前能否完成 | 断点 |
|---|---|---|
| 「把 NSW 2025 年套利收益算出来」 | ✅ | — |
| 「这是我那个 200MW/400MWh 项目的第一版测算，存下来」 | ❌ | 无项目实体；`saved_report` 只存报告不存参数上下文与版本谱系 |
| 「三个月后政策变了，我重算一版，和旧版对比」 | ❌ | 无版本化挂载；`assumptions_registry` 是全局单值，无法表达「项目 A 用压缩因子 0.92、项目 B 用 0.88」 |
| 「这个项目现货价差跌破阈值时提醒我」 | ⚠️ 半 | `alerts.py` 有 `evaluate_alert_rules(db, workspace_id=...)`（L183-185）与站内/邮件/webhook 三通道，但**告警规则挂在 workspace 而非项目**，且无项目级标的 |
| 「把这个分析链接发给投资委员会同事」 | ❌ | 筛选状态不落 URL（§6.1） |

### 2.3 结论

引入 `asset_project` 业务对象是本轮**最高价值的单点改造**：它把 7 阶段结果从「一次性的 HTTP 响应」变成「版本化的项目资产」，并顺带解锁版本对比、项目级告警、投后跟踪、Excel 导出复用同一套挂载关系。详见规划批次 R4。

> 用户 2026-09-05 决策：**自建极简埋点，不引入 PostHog**。（规划阶段曾评估 PostHog 自托管：完整栈需 ≥4GB，而生产 `mem_limit` 合计仅约 4.5GB —— backend 1500m / worker 1536m / postgres 1024m / redis 256m / web 384m，同机共存必然 OOM；且往主 compose 加服务会让 `deploy.sh` 的「四服务 running」验证失败并触发回滚门控 `ci.yml:343-344,430-434`。故自建恰好绕开这两重风险。）

### 6.3 「改参数不重算」不是产品缺陷，是两个同源 bug

这是本轮**从模糊抱怨定位到具体行号**的最有价值案例。原诊断为「前 5 阶段不响应 BESS 参数变更」，读代码后确认根因是 `web/src/hooks/useInvestment.js`：

```javascript
const body = {                    // L30-34：body 里根本没有 BESS 参数
  market: queryParams.market,
  region: queryParams.region,
  year: filters.year,
};
// ...
}, [filters.year, filters.region, filters.month, filters.quarter, filters.dayType]);  // L54：deps 含 month/quarter/dayType
```

两个 bug 同源：
1. **改 BESS 参数 → 不重算**：参数不在 body 里，也不在 deps 里。
2. **改月/季度/日类型 → 无效重算**：deps 变了，触发一次 POST，但**发出的 body 与上次完全相同** → 白花一次全量计算（后端 MILP 很重，见 §6.5）。

同时它用的是**裸 `useState`/`useEffect` 而非 React Query** → 无 key 化缓存，切换 workspace/来回导航都重打网络。`useStageSummaries.js`（L22-46）同病：4 个并行 `fetchJson`、无 AbortController、非 React Query。

**结论**：这个问题**不需要引入任何新的近似算法**就能大幅改善。修 bug + 接已有降采样，就是本轮计算性能的主方案（见 §6.5）。

### 7.2 ⚠️ P0 阻塞项：开放自助注册会激活一个设计级身份缺陷

这是本轮诊断中**严重度最高、且在既有文档中从未被记录**的发现。它不是端点 bug，而是**多租户身份模型的信任锚缺失**。

**证据链（全部已直读代码）**：

1. `access_control.py:907-946` `ensure_organization_membership_from_domain_policy`：当 `domain_record.get("join_mode") == "domain_auto_join_org"`（L928）时，**直接 `seed_organization_membership(..., role="org_member", status="active")`** 授予活跃成员资格（L931-937）。即：**域名匹配 = 授权入组织**。
2. `server.py:4739-4745`：登记 `organization_domain` 的端点只做 `check_organization_permission(_org_actor, "org_manage")` → **任何 org_owner 都能登记任意域名，且全链路无域名所有权验证**（无 DNS TXT、无验证邮件）。
3. `server.py:4698-4703`：同理，**任何 org_owner 都能自助创建 `oidc_provider` 记录并置 `enabled`**。
4. `access_control.py:979-985` `join_organization_by_domain`：principal 不存在则直接 `seed_principal`（**无邮箱验证**）；principal 存在但**无 `password_hash` 时，密码校验整段被跳过**（`if principal.get("password_hash") and principal.get("password_salt"):` 守卫为假即静默放行）。

**为什么现在是潜在的、开放注册后是活的**：平台当前邀请制，攻击者无法自助获得 `org_manage` 权限。一旦按本轮决策开放自助注册，**任何人都可以**：注册组织 → 登记 `gmail.com` 等公共域名（无验证）→ 开启 `domain_auto_join_org` → 获得「任意 `@gmail.com` 邮箱被判定属于该组织」的能力（域名劫持 + 钓鱼素材 + 阻塞真实域名所有者登记），并可对**无密码 principal** 走通 `join_organization_by_domain` 的密码跳过分支。

**必须与注册同期或更早修复**（规划 P0.3 / P0.4）：域名登记需验证（DNS TXT 或 postmaster 邮件）后才具备授权能力；`domain_auto_join_org` 与 OIDC/OAuth 自动入组织一律要求 `verified`；公共邮箱域名黑名单；关闭 `join_organization_by_domain` 的密码跳过分支。

> ⚠️ **实施注意（本地实测数据）**：当前 dev 库 `organization_domain` 已有 **94 行**、`oidc_provider` **97 行**、`principal_identity` **1863 行**（`tests/support.py:46` 的 `reset_pg_tables` 文档证实所有 DB 测试共享同一 PG 库，故其中大量为测试残留）。新增 `verified` 位时**必须决定既有行的回填策略**：全部置未验证会打断既有 auto-join 流程，全部置已验证则对既有行保留漏洞。这是一个需要显式决策的迁移点，不能默认处理。

### 7.3 另两个必须在本轮处理的安全敞口

**A. 匿名 bootstrap 被授予 owner 角色**（`auth_routes.py:132-152`）
`_ensure_bootstrap_identity` 给 `pr_websession` 对 `ws_default` 授 `"role": "owner"`。结合同站点 Origin 门控自动签发 + `update_subscription` 只校验 owner → 匿名可越权改套餐（见 §3）。文件末尾 L30 自述「该端点是 OIDC 人工登录接入前的权宜方案」→ 与本轮接入社交登录的决策正好对齐，应当收口。

已核实的实施要点：
- `tests/test_auth_web_session.py`（14 个测试）对 role/owner/membership **零断言**（grep 无命中）→ 降权不打破它。
- 但 `_ensure_bootstrap_identity` 是 **upsert 幂等**，既有部署的 `m_webbootstrap` 行**已固化为 owner** → **单改代码字面量对既有部署无效**，必须补一次性降权 UPDATE，并用环境变量做双向幂等的零代码回滚。
- 正确实践必须保留：`_client_ip`（L63-74）优先 `X-Real-IP`、**刻意不用 X-Forwarded-For 首段**（CWE-348 可伪造）。

**B. 既有 OIDC callback 是自证式认证端点**（`server.py:4851-4864`）
`subject`、`email`、`email_verified`、`display_name`、`expected_state`、`expected_nonce` **全部作为客户端 query 参数接收**。无 code exchange、无 token endpoint 调用、无 ID token 签名验证。且 L4866-4869 的 `state != expected_state` / `nonce != expected_nonce` 校验中，**两侧都来自客户端** → 攻击者把同一值传两次即可通过，这是**自证式校验，不是校验**。

实际门槛（限制了当前暴露面）：需要目标组织有 `enabled` 的 `oidc_provider`（L4871-4873）、workspace 归属匹配（L4875-4877）、**email 域名是该企业已登记域名**（L4879-4882）、且目标 principal **已有该 workspace membership**（L4898-4900）。

→ 因此今天它**不是**跨租户任意账号接管；但它把「域名登记」当授权凭据（与 §7.2 同源），且对已配置 SSO 的组织构成「无凭据登录」路径。

**关闭它零损失的决定性理由**：因不存在 code exchange，**今天没有任何真实 IdP 能通过它完成认证** → 它提供零合法功能，只有风险。故：默认关闭（环境变量门控）+ 另立独立任务重写为真实 code exchange + JWKS 验签（需同步改 `tests/test_oidc_auth*.py` 的 14 个测试，高风险，不与本轮混做）。

**C. 密码哈希强度偏低（对既有推测的纠正）**
实读 `access_control.py:201-202`：

```python
def _hash_password(password: str, salt: str) -> str:
    return hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), bytes.fromhex(salt), 120000).hex()
```

即 **PBKDF2-SHA256、12 万次迭代**（规划早期有智能体推测「应确认是否为 argon2/bcrypt」，此推测错误，以本直读为准）。算法选型本身没问题，问题是迭代次数在 2026 年偏低 → 提至 60 万级别，并**在登录成功后按「存储迭代数 < 当前」透明重哈希**（需在 principal 侧记录迭代数）。**不换算法**，以避免全库重哈希与登录风暴。

### 7.4 状态外置是「开放注册的容量前提」，不是性能优化

6 处进程内内存态在 `GUNICORN_WORKERS > 1` 时按 worker 数**线性放大**（限流被绕过 N 倍、去重失效）：

| 位置 | 内容 | 多 worker 后果 |
|---|---|---|
| `access_control.py:43` | `_login_attempts`（deque，**成功才清**） | 登录限流被放大 N 倍；失败尝试按 email 无上限增长（内存泄漏） |
| `auth_routes.py:60` | `_bootstrap_attempts`（`dict[str, list[datetime]]`） | 签发限流被放大 N 倍 |
| `investment_routes.py:46-51` | `_ANALYSIS_INFLIGHT` | 重复全量计算不再被去重 |
| `coopt_routes.py:33-34` | `_COOPT_CACHE`，**max 50 且无 TTL** | 陈旧结果 + 配额判断失真 |
| `account_routes.py:674-726` | `_quota_cache` / `_quota_cache_ts`（60s TTL） | 各 worker 配额视图不一致 |
| `services/pipeline_knowledge.py:34-47` | 模块级 `_cache`，**永不失效** | 改 JSON 必须重启；多 worker 各持一份 |

解法：限流/inflight/配额 → Redis；两处缓存 → 加 TTL 或 Redis 化。容错**复用 `response_cache.py:16,29-40` 已有的 circuit breaker**（`_CIRCUIT_BREAKER_COOLDOWN_SECONDS=60`），不新造机制。

### 7.5 批次顺序（目标函数 = 公测期用户反馈最大化）

```
交付0（诊断落文档）

    → P0（安全前置·硬门）──── 未全绿不得开放自助注册
      → R1（完整用户体系：注册/验证/OAuth/管理UI/导出删除）

        → R5（自建极简埋点 + feature flag + 控制台/激活指标）
        → R6（Excel/HTML邮件/StatusPage/方法论页/图表层/i18n）
```

排序理由（以「最快拿到真实用户反馈」为准）：
1. **P0 先于 R1**：安全前置是注册的硬门，且写端点守卫零风险可最先发布。
2. **R1 先于一切体验优化**：没有注册就没有「用户」，后续所有反馈都无法归因到人。
3. **R3 紧随**：URL 可分享是**成本最低、传播收益最高**的一项（复用 `toQueryParams` + nginx 已就位）。
4. **R4 与 R5 并列**：`asset_project` 决定「是否有人愿意留存」，埋点决定「我们能否知道为什么」。
5. **R6 靠后**：Excel/Status Page 是留存与信任增强，在激活链路打通之前做是浪费。
