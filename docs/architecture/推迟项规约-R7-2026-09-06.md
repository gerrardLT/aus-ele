# R7 推迟项规约（2026-09-06）

来源：《公测商业化缺口诊断与产品化路线-2026-09-05》（docs/strategy/）决策表 §8 与 §6.4–6.6。
本文把散落在诊断各处的「本轮不做」收拢成一份可执行规约：每一项给出**推迟理由**（引用证据）
与**解除前置**（重启前必须先满足的条件）。规约不是「永远不做」，而是防止在不满足前置时
顺手开工 —— 诊断原话：**半成品安全功能比不做更糟**。

## 1. 结构性推迟（架构决策）

### 1.1 不拆 server.py

- **理由**（诊断 §6.6）：跨语言源码锁 —— `web/src/lib/aemoConvergence.test.js` 与
  `aemoDecisionClosure.test.js` 用 `fs.readFileSync` 读后端源码断言 9 个契约字面量
  （`recommendation_summary`/`explanation_chain`/`risk_boundary`/`value_stream_coverage`/
  `readiness_status`/`Reserve Opportunity`/`Market Entry Readiness`/`decision-grade`/`preview_only`），
  而 `node --test src/lib/*.test.js` 是 CI 唯一硬阻断门（ci.yml:106）。且
  `app.py:116,161`、`admin_routes.py`、`investment_routes.py` 全部 `import server as _server`
  —— 它是运行时依赖枢纽，不只是路由集合。
- **b3 后现状更新（2026-09-06）**：22 个死副本端点已去装饰器，端点实现真源迁入
  `routes/*.py`；上述前端锁的扫描范围已同义扩为「server.py + routes/*.py served 合集」，
  字符串锁本身不变。aemoDecisionClosure 锁定的 5 个 P3 决策字符串仍在 `server.py`（约
  L847-956）未动。**「不拆」的准确含义已从「不搬任何代码」收窄为「不动 P3 决策逻辑与
  依赖枢纽」**。
- **解除前置**：①5 个 P3 字符串的迁移方案（含跨语言锁同步改）过评审；②改 `main.jsx`
  类似规模的「无法灰度」变更要有双通道（旧入口保活）方案；③本地实跑后端全量（CI 后端
  测试是哑门，诊断 §6.5）。

### 1.2 不引入 react-router

- **理由**（诊断 §6.4/L215）：`mainEntryPerformance.test.js:14-18` + `finlandBoard.test.js`
  + `developerPortal.test.js` 对 `main.jsx` 的**精确 lazy 串断言**（唯一硬阻断门）+
  14 层三元 → `<Routes>` 无法灰度。体积余量只是次要理由（体积预算门是非阻断的）。
  c1（方法论白皮书页）又新增 1 个三元分支 —— 精确断言与三元链的耦合仍在加深。
- **解除前置**：三个精确断言测试与三元链的替换方案过评审；URL 状态镜像
  （`pageRouter.js` + `toQueryParams`）与新路由库的职责边界写清；同样受「无法灰度」
  约束，需双通道方案。

### 1.3 不重写 translations.js

- **理由**（诊断 §6.4）：58.5KB 被 10 个文件静态 import，`FilterBar.jsx:13` 在**首屏
  关键路径**；同时被测试锁死（§6.6）。
- **新文案的规矩**：新命名空间独立文件 + 合并既有对象（而非改写）；散落的
  `lang === 'zh' ? :` 不清理，只在新代码里避免。

### 1.4 不做服务端 PDF / intraday 管道 / 工单系统

- **理由**（决策 7）：服务端 PDF 与 Excel 导出、客户端打印路径重叠，优先级低于数据
  可信类缺口；intraday 管道依赖新数据源接入与存储扩容；工单系统在免费公测期用
  反馈页 + 邮件渠道覆盖。
- **解除前置**：各自独立评估，无结构性障碍；工单系统重启前先把反馈页的响应时效
  承诺（运营节奏清单）跑顺。

## 2. 安全与商业化推迟（半成品比不做更糟）

### 2.1 不做 TOTP 2FA

- **理由**（决策 7）：TOTP 需要配套恢复码、限流、审计与客服找回流程；只做「扫码绑定」
  半成品会把用户锁在账户外，比没有 2FA 更糟。
- **解除前置**：恢复码/限流/审计三个配套的设计文档齐备后再开工；当前防线（密码策略
  PBKDF2 120k + 会话外置 Redis + 登录限流）维持。

### 2.2 收费/支付全套

- **理由**（决策 1）：用户 2026-09-05 明确「免费公测，用户反馈第一」。PricingPage 的
  套餐仅为展示（ctaKind=contact，无支付链路，pricingCopyGuard 锁定）。
- **解除前置**：法人主体/ABN/ACN/管辖法域落定（诊断 §9.2 人工核验项）+ 退款/税务
  条款入 `/legal/terms` + 发票与收款通道选型。

### 2.3 不引入 PostHog 等第三方分析

- **理由**（决策 6）：自建极简埋点已 wired（R5.1/R5.4）；第三方 SDK 属在线子处理者，
  引入前必须先改 `/legal/dpa` 第 4 条与 `/legal/cookies` 第 7 条（先采集后公示 = 对用户
  提供不实陈述）。
- **解除前置**：法务条款先行（顺序纪律写在 `.env.docker.example` 的
  `VITE_ANALYTICS_ENABLED` 注释里）。

  `domain_data_validation.py` 白名单。

## 5. 解除流程

任何一项要重启：①在 `docs/tasks/` 开任务记录；②对照「解除前置」逐条确认并在任务记录
里留证；③评估对唯一硬阻断门（`node --test`）与后端全量（本地实跑）的影响面；④按批次
纪律提交（新功能/新测试一批，既有代码既有测试不混批）。
