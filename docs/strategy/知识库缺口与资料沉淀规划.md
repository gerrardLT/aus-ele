# 知识库缺口与资料沉淀规划

更新时间：2026-08-12

适用范围：
- Agent 系统（`backend/agent/`）的知识供给
- 全平台可信度与可审计性建设
- 与 `docs/strategy/竞品地图与差异化定位建议.md` 中 Rule-aware Decision Layer 路线对齐

本文回答两个问题：
1. 对这个 Agent 和当前系统，我们还缺哪些知识库？
2. 每类资料怎么沉淀、由谁消费、按什么节奏维护？

核心判断：

`Agent 的上限不取决于 LLM，而取决于它背后沉淀了什么。`

当前 Agent 的数值全部来自系统内数据（工具级溯源 + grounding 校验），但"规则、假设、案例、基准"四类知识要么散落在代码里，要么靠 LLM 参数知识裸答——这是当前可信度链条上最薄弱的一环。

## 2. 分项规划

### 2.1 规则与制度知识库（P0，首版已完成 2026-08-12）

> **实施状态**：`data/knowledge/grid_rules.json`（NEM 6 卡 + WEM 3 卡 + 8 条政策时间线，每条含四要素）；`backend/services/grid_knowledge.py` 确定性检索服务；Agent 工具 `grid_knowledge_lookup`（Global 阶段，接入 stage1/stage2/stage6 profile + 关键词路由）；人读版 `docs/_references/电网规则知识卡片-2026-08.md`；测试 `tests/test_grid_knowledge.py` 10 用例全绿。剩余：卡片扩充（网络费/注册分类细节/Operating Reserve 落地后更新）。

**现状**：政策知识只存在于策略文档（给人看）；Agent 答规则类问题靠 LLM 内置知识，存在时效风险（AEMC 规则逐年变化：2025 MPC/CPT 更新、IESS 规则落地等）。

**沉淀内容**：
1. NEM 规则卡片：注册类别（IESS / bidirectional / PFR 义务）、价格上下限、MPC/CPT 参数、5 分钟结算机制、FCAS 服务规格
2. WEM 制度卡片：RCM 机制、BRCP 定价逻辑、ESS 服务集、Supplementary Capacity 触发历史
3. 政策时间线：每条规则 = `生效日 + 影响的价值流 + 受影响的系统模块`

**格式要求**：
- 结构化 JSON（供 Agent 工具检索）+ 人读 Markdown（供团队评审）
- 每条知识四要素：`source_url / effective_date / confidence / review_date`

**消费方**：
- 新工具 `grid_knowledge_lookup`（沿用 benchmark 工具的接入模式：知识库 + lookup 工具 + profile 暴露）
- `narrative_attribution`、Agent 系统提示词的规则语境

**维护节奏**：季度评审 + 重大规则变更即时更新。

### 2.2 参数与假设登记库（P0，首版已完成 2026-08-12）

> **实施状态**：登记表与 `backend/services/assumptions_registry.py` 已上线；首批 7 项登记（2 项 wired：FCAS 压缩因子、benchmark 参考电池；3 项 audit_only；2 项 pointer）；硬性规则已写入 AGENTS.md 第 6 条；测试 `tests/test_assumptions_registry.py` 含"引擎常量与登记表一致性"护栏。剩余：audit_only 项逐步迁移为 wired。

**现状**：关键假设散落各处——FCAS 压缩因子 0.3（`agent/tools.py` 硬编码）、RTE 0.85/0.87、CAPEX 曲线、蚕食率、贴现率、CIS floor / BRCP 占位值（`data/contract_revenue_defaults.json`）。改一个要翻代码。

**沉淀内容**：统一假设登记表，每个参数一行：

| 参数 | 取值 | 依据来源 | 最后校准日 | 适用边界 | 修改人 |
|---|---|---|---|---|---|

首批登记对象（已知散落点）：
- `FCAS_COMPRESSION_FACTOR = 0.3`（agent/tools.py）
- 参考电池参数 100MW/200MWh/RTE 0.85（benchmark_engine.py）
- CIS floor 75,000 AUD/MW/年、BRCP 11,500（占位，待官方值替换）
- 网络费默认值（regional_fee_defaults.json）
- 蒙特卡洛与蚕食模型的分布参数

**格式**：`data/assumptions_registry.json`，代码逐步改为从登记表读取。

**消费方**：投资测算可审计性（融资尽调必答"这个参数哪来的"）、快速调参、回归测试基准。

**维护节奏**：参数变更必须同步更新登记表（写入 AGENTS.md 硬性规则）。

### 2.3 市场事件案例库（P1，首版已完成 2026-08-13）

> **实施状态**：`data/knowledge/market_events.json` 首批 5 案例（SA 黑系统 2016 / Liddell 退役 / 负价潮 2025Q4 / FCAS 崩塌 / 收益创新低 2026），每卡含因果结构与教训；`backend/services/market_events.py` 检索服务；Agent 工具 `market_event_lookup`（接入 stage2_revenue / stage4_outlook profile + 路由关键词）；人读版 `docs/_references/市场事件案例卡片-2026-08.md`；测试 10 用例全绿。剩余：埋点（Agent 经验库）单独推进；WEM 事件待补录。

**现状**：`event_annotation_service` 骨架存在，案例积累薄。

**沉淀内容**：重大事件因果卡片，每张：

`事件描述 → 价格/FCAS 影响 → 持续时长 → BESS 当时实际表现 → 对未来的启示`

首批必录事件：
- 各州黑系统事件与价格尖峰（含 SA 历史大停电）
- 煤电退役节点（Liddell 等）对价差结构的影响

- FCAS 价格崩塌过程（2024-2026，10 服务全 collapsed）
- 2026 年 3-5 月 NEM 储能收益连续创新低

**消费方**：`narrative_attribution` 归因叙事、"历史相似情景"检索、benchmark 异常解释。

**维护节奏**：事件驱动（发生即录），季度整理归档。

**维护节奏**：季度更新（AEMO 季度管线报告发布后）。

### 2.6 Agent 经验库（P1，汇总层已完成 2026-08-13）

> **实施状态**：埋点已存在（`agent_execution_log` 表，每次运行落库 query/steps/status/duration，无需新埋点）；新增 `backend/services/agent_experience.py` 汇总服务（意图聚类 8 类 + 工具调用频次/失败率 + 未使用工具发现 + 慢查询/失败案例抽样）；端点 `GET /api/v1/agent/experience-summary?days=30`（鉴权）；测试 11 用例含注册表一致性护栏。剩余：月度汇总归档与 few-shot 范例库（随线上用量积累后推进）。

**现状**：有 golden trajectories 离线测试，线上真实问答无系统性回收。

**沉淀内容**：
1. 真实问题日志 → 分类统计：高频问题、答不好的问题、从未被调用的工具
2. judge 判优的好答案 → few-shot 范例库
3. 问题-能力缺口映射：用户问了但系统答不了的 → 反哺知识库需求（本清单的持续来源）

**消费方**：工具路由调优、提示词迭代、产品路线图。

**维护节奏**：埋点持续采集，月度汇总分析。

## 3. 统一沉淀标准

1. **双格式**：机器可读 JSON（Agent 检索）+ 人读 Markdown（团队评审）
2. **存放位置**：机器数据入 `data/knowledge/`（需评审入库）；人读文档入 `docs/references/` 或 `docs/strategy/`
3. **每条知识四要素**：来源 URL、生效/采集日期、置信度、复审周期
4. **接入模式**：沿用 benchmark 工具成熟套路——知识库文件 + lookup 工具 + profile 暴露；不做重型 RAG（数据量级到了再上）
5. **变更纪律**：参数/规则变更必须同步知识库并记录修改人与日期

## 5. 与差异化定位的关系

竞品调研结论中我们的空位是"比数据门户更懂储能决策、比投标系统更轻更易懂、比咨询报告更实时"。知识库建设直接支撑这个定位：

- 规则库 → "规则感更强"的产品承诺兑现
- 假设登记库 + 校准记录 → 可信度护城河（竞品黑箱做不到的可审计性）
- 事件案例库 → 解释链深度（解释型产品的核心资产）
- 经验库 → 持续发现真需求，避免闭门造车
