# 分析埋点：Cloud 启用与自托管迁移路径（R5.2，2026-09-06）

本文是 `docs/deployment/运营节奏清单.md` 的配套页：**只有要动 `VITE_ANALYTICS_*` 这一组开关的人才需要读它**。
产品默认不启用任何第三方分析（`web/src/lib/analytics.js` 的默认状态是 `disabled`，零副作用）。

---

## 0. 三条不可违反的顺序

| 顺序 | 约束 | 违反的代价 |
|---|---|---|
| **1** | **先改法务文本，再翻开关**。`/legal/dpa` 第 4 条与 `/legal/cookies` 第 7 条当前写的是「未启用第三方分析，启用前会先公示」 | 隐私承诺与实际行为不一致 —— 这是我们自己在隐私页第 5 条上刚修过的那类不实陈述 |
| **2** | **回放（session replay）必须与两个遮蔽开关同时启用**。`isRecordingEnabled()` 要求 `VITE_ANALYTICS_MASK_ALL_TEXT` 与 `VITE_ANALYTICS_MASK_ALL_INPUTS` **同时**为 `true` | 半截遮蔽不算遮蔽：财务模型页面上「只遮输入框」等于把 IRR、收益数字整屏录走 |
| **3** | **后端不发埋点**。`analytics.js` 只采前端行为；服务端已有 OpenTelemetry（`backend/telemetry.py`、`backend/openlineage_support.py`），Spec R5.6 明确否决第二条埋点链路 | 两套埋点 = 两套会互相矛盾的「有多少人用了」数字 |

## 1. 关键事实：`VITE_*` 只有构建期一条注入路径

`import.meta.env.VITE_*` 是 **打包时被替换成字面量**的。因此：

* 改 nginx / compose 的运行时环境变量**不会**改变已发布 bundle 里的取值；
* 翻任何一个 analytics 开关 = **重新构建 web 镜像**，不是 `docker compose restart web`；
* 所以「有读者但没人拧得动」是真实风险。三个必须同时存在的位置，由 `web/src/lib/flagsGuard.test.js`
  最后一道断言常驻检查（缺任意一处即测试变红）：

| 位置 | 作用 |
|---|---|
| `web/Dockerfile` 的 `ARG` + `ENV` | 让值真正进构建环境 |
| `docker-compose.yml` 的 `web.build.args` | 让本机/自建部署拧得动 |
| `.github/workflows/ci.yml` 的 `vars.VITE_*` → `--build-arg` | **生产镜像唯一开关**（`docker-compose.prod.yml` 只 pull 现成镜像） |

生产开启方式：仓库 **Settings → Secrets and variables → Actions → Variables** 里设置下列变量，然后触发一次
正常发布构建。未设置的变量会被整体跳过，落回 Dockerfile 里的默认值（一律「关」）。

## 2. 选项 (a)：PostHog Cloud —— 本轮默认采纳

### 2.1 需要设置的仓库 Variables

| 变量 | 值 | 说明 |
|---|---|---|
| `VITE_ANALYTICS_ENABLED` | `true` | 只认字面量 `true`（`1/yes/TRUE/on` 一律视为关，见 `flags.js`） |
| `VITE_ANALYTICS_SDK_URL` | `https://us.i.posthog.com/array.js`（或 eu 域） | 动态 `<script>` 的 src，**不进 bundle** |
| `VITE_ANALYTICS_TOKEN` | `phc_...` | **必须是客户端 public key**。ARG 值会留在镜像历史里，任何服务端写权限密钥都不得走这条路径 |
| `VITE_ANALYTICS_HOST` | 与 SDK_URL 同域 | 上报目标 |
| `VITE_ANALYTICS_SESSION_REPLAY` | 默认不设（`false`） | 只有配合下面两项才生效 |
| `VITE_ANALYTICS_MASK_ALL_TEXT` | `true` | 回放前置条件 1 |
| `VITE_ANALYTICS_MASK_ALL_INPUTS` | `true` | 回放前置条件 2 |

### 2.2 端点选择

数据驻留按用户主体所在地选 region（澳洲用户 → `us` 或 `eu` 均可，需在公司隐私政策里写明处理地与
跨境传输依据）。**选定后不要改**：换 region = 换项目 = 历史数据分裂成两截。

### 2.3 上线后的自查（5 分钟）

1. 构建产物里不应出现 PostHog 代码：`npm run build` 后 grep `dist/assets/index-*.js` 里的 `posthog`
   —— 只应有 `createElement('script')` 的字符串，不应有 SDK 实现（`analytics.test.js` 已锁这条）。
2. DevTools Network：确认事件带的是 public token，且**请求体里没有任何查询文本、项目名、财务数字**。
3. 属性白名单是 key 级黑名单（`DENIED_KEY`）+ 值含 `@` 直接丢，**它不是完备防线**：新增埋点时
   请先看 `analytics.test.js` 的「event properties are allowlisted」那条断言，把想传的字段名过一遍。

## 3. 为什么**不**把 PostHog 加进主 `docker-compose.yml`

这两条是实测约束，不是偏好：

1. **CI 冒烟门会必然失败**。`.github/workflows/ci.yml` 的部署前校验按「四个服务、120s 内 healthy」
   写死（见 `ci.yml` 的 smoke 阶段与 `deploy/scripts/lib/smoke.py`）。PostHog 全栈首次启动要跑迁移并
   等 ClickHouse 就绪，远超 120s，且会让「服务数=4」这一前提在多处脚本里失效。
2. **内存预算根本不够**。主 compose 的 `mem_limit` 合计约 4.5GB（backend/postgres/redis/web），
   而 PostHog 官方自托管镜像的最低建议值就是 ≥4GB —— 加进来不是「挤一挤」，是在同一台机器上
   制造必然 OOM，被挤掉的会是承载生产读路径的那几个。

结论：自托管必须走**独立的 compose 文件 + 独立的机器**，不能寄生在主栈里。

## 4. 选项 (b)：自托管迁移路径（保留，不默认执行）

### 4.1 什么时候该迁

| 触发条件 | 为什么 |
|---|---|
| 单月事件量使 Cloud 账单超过一台机器的月成本 | 纯经济判断 |
| 客户尽调要求「行为数据不出我们控制的机房」 | To B 销售的实际阻塞项 |
| 需要查询原始事件表（Cloud 上导出受限） | 分析自由度 |

**未触发前不要迁**：自托管 PostHog 是一套需要人维护的有状态系统（迁移、备份、版本升级），
公测期的工程时间应该花在产品上。

### 4.2 独立栈的形状

新建 `deploy/docker-compose.analytics.yml`（**不要**加进 `docker-compose.yml`），至少包含：
`web`、`worker`、`db`（Postgres）、`redis`、`clickhouse`、`zookeeper`、`kafka`（或 PostHog 新版本
的 all-in-one `posthog` 镜像 + 外置 PG/CH）。要点：

* **数据盘与备份**：`clickhouse` 与 `db` 两个卷必须进现有备份脚本（`deploy/scripts/`），
  否则「迁自托管」等于「把行为数据从有备份的地方搬到没备份的地方」。
* **不共用主栈的 Postgres/Redis**：连接串隔离。主栈 `postgres` 已是共享开发+生产库，
  再塞一个分析写负载会让读路径抖动。
* **反向代理同域**：把 `/ingest` 反代到 posthog，浏览器侧与站点同域，避免第三方 Cookie/广告屏蔽
  把上报整段吃掉（这是 Cloud→自托管最常见的「数据突然归零」原因）。

### 4.3 迁移步骤（顺序不可反）

1. 起自托管实例，建项目，拿到**新的** public token；
2. 在自托管实例的项目设置里**先**打开 `mask_all_text` / `mask_all_inputs`（前端与后台互不信任，
   两边都要声明，见 `analytics.js` 的 init 逻辑）；
3. 在法务文本里把处理者/机房所在地改为自托管主体，并完成隐私政策变更公示；
4. 改仓库 Variables：`VITE_ANALYTICS_TOKEN` / `_HOST` / `_SDK_URL` 指向新实例；
5. **重新构建并发布 web 镜像**（构建期开关，重启无效）；
6. 观察 48h：确认新旧实例都有事件流入 → 在 Cloud 侧导出历史数据（`Export events` 到对象存储）
   后停用；
7. 历史数据是否需要合并进自托管：默认**不合并**。两套实例的事件 ID/用户 ID 语义不完全一致，
   强行拼接造出来的趋势线会被当成真数据引用。以发布日为界分段说明即可。

### 4.4 回滚

分析是**纯加法**：`VITE_ANALYTICS_ENABLED` 不设（或设为非 `true`）→ 重新构建 → 采集彻底停止，
`capture()` 变 no-op、不注入 `<script>`、不排队。回滚不需要动任何业务代码或数据库。

## 5. 隐私边界（与埋点实现一同被测试锁定）

* 身份用 `principal_id`，**永不上传邮箱**：`identify()` 显式拒绝含 `@` 的 id（`analytics.test.js`）。
* 事件属性只允许低基数枚举值；`query/search/text/name/project/email/amount/irr/url/...` 一类
  key 直接拒收。
* SDK 未就绪时事件在内存队列里暂存，队列有上界，加载失败即整段丢弃（不无限期留存用户行为）。
* 配置半截（开关开了但缺 URL/token）时状态为 `unconfigured`，**不入队**：没有消费者却攒队列
  等于把用户行为长期留在内存里。
