### P0.6 PBKDF2 迭代 120k→600k + 登录透明重哈希 — ✅ 已完成（2026-09-06）

换算法会让存量账户全部失效，因此走**参数化 + 渐进迁移**：`principal` 表惰性补 `pw_iters INTEGER` 列（NULL = 迁移前 120k 基线），登录成功时按存储迭代数校验、必要时用目标迭代数重算写回。

关键实现约束（三条都是踩过的坑）：

1. `database.py:upsert_principal` 是**硬编码列清单**，新列必须在 INSERT / ON CONFLICT / 参数三元组三处同步加，否则被静默丢弃；
2. 加列后该函数会在冲突时写 `pw_iters=excluded.pw_iters` → 任何不带 `pw_iters` 的 `{**principal}` 调用会把值清成 NULL，哈希被当作 120k 验证 → **用户被锁死在门外**。故 `fetch_principal` 与 `fetch_principal_by_email` 两个读路径都必须返回它；
3. `_pbkdf2_iterations()` 用 `max(FLOOR, requested)` 钳制，防配置把迭代数调低（降哈希强度不可逆）；`_stored_iterations()` 把 NULL/脏值一律按基线处理。

时机是硬约束：**只有密码已被验证正确之后才有权改写凭据**，否则该分支退化成账户接管。重哈希失败不得打断已认证的登录，降级 warning + 审计 `principal.password_hash_upgraded`。

证据：`tests/test_password_hash_upgrade.py`（14 tests，全绿）。决定性用例是 `test_wrong_password_does_not_rewrite_hash`（错误密码后 hash 与 `pw_iters` 均原样保留）与 `test_rehash_failure_does_not_break_authenticated_login`。存量哈希用 `hashlib` 独立算出（`_legacy_hash()`），不用被测函数自证。

### P0.7 状态外置 Redis — ✅ 六站点全部接线（2026-09-06）

新建 `backend/shared_state.py`：`SlidingWindowLimiter`（有界 4096、按最早时间戳淘汰）+ `SharedStateStore`（限流 / 带 TTL 的 JSON 缓存 / 认领锁），单例走 `get_state_store()`。容错不新造一套 —— 熔断复用 `response_cache.RedisResponseCache`，只在 `_redis()` 这一唯一收口补了「构造失败也计入熔断」。

| 站点 | scope | 顺带修掉的原实现缺陷 |
|---|---|---|
| `access_control._check_login_rate_limit` | `login_rl` | `_login_attempts` 失败路径**永不回收键**（内存泄漏） |
| `auth_routes._check_bootstrap_rate_limit` | `web_session_bootstrap_rl` | check-then-append **之间无锁**，同 worker 并发可穿透 |
| `account_routes.check_invite_accept_rate_limit` | `invite_accept_rl` | 同类 TOCTOU + 键无限累积；R1 自助注册的 token 探测唯一防线 |
| `pipeline_knowledge._load_capacity_data` | `capacity_knowledge` | 原 `_cache` **永不失效**（改 JSON 必须重启）；补 TTL 300s + 负缓存 30s + public `clear_capacity_cache()` |
| `coopt_routes` 结果缓存 | `coopt_result` | 原 max 50 **无 TTL**；`next(iter(dict))` 淘汰的是最早插入项、不是最久未用（LRU 名不副实）→ 改按 expires_at 淘汰 |
| `investment_routes._acquire_inflight_entry` | `analysis_inflight_claim` | 跨 worker 完全不去重（最贵的 MILP 各算一遍） |

`_today_usage` 的配额缓存把 **day 一起存进值里**：TTL 60s 跨过 UTC 零点时不能拿昨天的计数报今天，读侧按 day 不匹配直接重算。`update_subscription` 的失效改成跨 worker 生效（原先只 pop 本进程 dict，切套餐后其他 worker 仍最长 60s 报旧视图）。

**分工刻意不对称**：「谁在算」（认领信号）→ shared_state（需要原子 SET NX、秒级存活）；「算完的结果」→ 沿用已有的共享 `analysis_cache` 表。不把大 payload 复制进状态命名空间，也因此 Redis 完全不可用时行为严格不劣于外置之前。

超时语义**刻意不降级为「那我自己算」**：一次超过等待窗口的慢分析会把所有并发请求转成重复计算，负载被放大成 O(请求数 × 单次成本)，故维持原有 503。

证据：`tests/test_shared_state.py`（26）+ `tests/test_analysis_inflight.py`（13）全绿。其中两条是红测试倒推出来的真缺陷：

- `test_failing_redis_client_falls_back_instead_of_raising` → `_redis()` 原先在 try 之外调用 `_get_client()`，`redis.Redis.from_url` 对畸形 URL **在构造阶段就抛**，而既有熔断只统计命令执行失败 → 拼错一个 `REDIS_URL` 会让每个被限流/缓存的端点 500。已在 `_redis()` 收口，并同步修 `response_cache.get_json`/`set_json` 的同源洞（全应用受益）。

**复用而非新造**（每一条都有既存同族实现）：一次性 token 表抄 `password_reset`；token 不外泄/用后即焚/发信失败撤销挑战抄 P0.3 域名验证；限流走 P0.7 `shared_state.register_attempt`；建号授权走 `access_control` 已有单测的 `seed_*` 五件套；`_get_actor` 从 `account_routes` 复用、`_client_ip` 从 `auth_routes` 复用（不再抄第三份）；`env_flags.env_flag` 收口 `server.py:1669` 与 `app.py:49` 两份逐字重复的 `_env_flag`。

**三条关键设计判定**（都写进了代码注释，此处只记结论）：

1. **注册当场签发会话**。未验证是软限制，只作用于新端点 + 前端 banner；硬要「验证完才发令牌」等于改 `authenticate_access_token` 的语义，会把 SMTP 故障放大成全平台不可用。
2. **占用检查在密码策略之后**。否则弱密码请求变成免费的邮箱枚举探针（422=密码弱、409=邮箱在 → 一次调用两个信号）。
3. **`email_verified_at` 是单调列**：`upsert_principal` 用 `COALESCE(excluded, 现值)`、`mark_principal_email_verified` 带 `AND email_verified_at IS NULL`。不这么做时，任何不带该列的 `upsert_principal`（如 `seed_principal` 构造）都会把已验证账户悄悄打回未验证 —— 这类倒退没有报错，只表现为 banner 常驻与权限提示错乱。

**写作时自查出的四个真实缺陷**（都是「先写红断言、再心算一遍」暴露的，不是跑出来的）：

- 弱密判定只做整串小写比对 → `"Password123!"` 放行，人类最常见变体全漏 → 加 `COMMON_WORD_STEMS` + `_stem()`（仅在 <16 位时判弱，避免误伤长口令）。
- 键盘行判定要求整串相等 → `"qwertyuiop12"` 放行 → 改为子串命中（含逆序）。
